# Задание: разместить «Робота-бухгалтера» на домашнем сервере

Адресат: системный администратор / серверный специалист.
Дата постановки: 2026-10-13.
Репозиторий: `https://github.com/mleontev111-max/robot-buhgalter`
Ветка для сборки: `claude/github-connection-q4t7zr` (см. раздел «Какую ветку брать»).

Цель: владелец должен открывать приложение со своих устройств в домашней сети,
подключать кабинеты Ozon / Wildberries / Яндекс Маркет по read-only API-ключам и
получать расчёт налогов по кварталам текущего года.

---

## 1. Что именно разворачивается

Два компонента, оба из этого репозитория.

**A. Frontend** — статика. Собирается в `dist/`, отдаётся веб-сервером.
Всё состояние (организации, операции, ключи) живёт в `localStorage` браузера
пользователя. Серверной базы у этого контура нет.

**B. Сервер синхронизации** — `server/index.mjs`, Node, порт по умолчанию `8787`.
Read-only прокси к API маркетплейсов: принимает от браузера ключ и период,
обращается к API маркетплейса, возвращает операции. **Ключи не хранит** —
они приходят в теле запроса и живут только на время запроса.

Чего в этом контуре **нет** — чтобы не было неверных ожиданий:

- нет серверной БД, нет учётных записей, нет разделения пользователей;
- нет фоновой синхронизации по расписанию — синхронизация запускается из
  интерфейса вручную;
- данные привязаны к браузеру и профилю устройства. Второе устройство увидит
  пустое приложение, пока в него не перенести резервную копию (JSON-экспорт
  из интерфейса).

Отдельный production-backend на PostgreSQL в репозитории есть
(`server/production/`, PR #3), но он **не нужен для этой задачи**: в нём есть
авторизация, организации и серверное хранение ключей, но нет ни загрузки
операций, ни расчёта налогов. Разворачивать его сейчас не надо.

## 2. Какую ветку брать

Ветка `main` работоспособна, но в ней нет части нужных правок. Собирать с
`claude/github-connection-q4t7zr`: в ней параметры налогов разведены по годам,
есть шифрование ключей на устройстве, 45 автотестов и — существенно для этой
задачи — адрес сервера синхронизации настраивается переменной сборки
(в `main` он жёстко задан как `http://localhost:8787`, что для размещения на
отдельном сервере не годится, см. п. 4).

Если ветка к моменту работ уже влита в `main` — берите `main`.

## 3. Требования к окружению

- Node.js 20 и npm (сборка frontend и запуск сервера синхронизации).
- Reverse proxy с TLS. Подойдёт Caddy (проще всего) или nginx.
- Исходящий HTTPS с сервера к:
  - `api-seller.ozon.ru`
  - `statistics-api.wildberries.ru`
  - `api.partner.market.yandex.ru`
- Доступ к приложению **только из домашней сети или через VPN**. В интернет не
  публиковать (обоснование — п. 6).

## 4. HTTPS обязателен, это не рекомендация

Два технических ограничения, оба жёсткие:

1. Шифрование API-ключей в браузере использует WebCrypto (`crypto.subtle`).
   Он доступен только в secure context — то есть по HTTPS либо на `localhost`.
   По обычному HTTP с другого устройства функция шифрования ключей просто не
   будет работать.
2. Страница по HTTPS не может обращаться к серверу синхронизации по HTTP —
   браузер заблокирует как mixed content. Значит сервер синхронизации тоже
   должен быть за HTTPS (проксируйте его тем же reverse proxy).

Варианты сертификата для домашнего сервера:

- свой домен + DNS-01 (Let's Encrypt) — предпочтительно, работает на всех
  устройствах без ручной установки;
- внутренний CA Caddy (`tls internal`) — проще, но корневой сертификат
  придётся доверить на каждом устройстве владельца.

Выбор за вами, оба приемлемы.

## 5. Шаги развёртывания

### 5.1. Сборка frontend

`VITE_SYNC_SERVER_URL` вшивается в бандл **на этапе сборки**. Указывать нужно
адрес, по которому сервер синхронизации доступен **с устройства пользователя**,
а не с сервера: запрос уходит из браузера. `localhost` здесь будет ошибкой —
телефон начнёт искать сервер у себя.

```bash
git clone https://github.com/mleontev111-max/robot-buhgalter.git
cd robot-buhgalter
git checkout claude/github-connection-q4t7zr
npm ci
VITE_SYNC_SERVER_URL=https://buh.example.lan/sync npm run build
```

Результат — каталог `dist/`. Отдавать его как статику, с fallback на
`index.html` (SPA-роутинг).

### 5.2. Сервер синхронизации

Слушать только loopback и выставлять наружу через reverse proxy.
`ALLOWED_ORIGINS` обязателен: по умолчанию разрешены только `localhost:3000` и
несколько внешних origin, ваш домен в этот список не входит, и браузер получит
ошибку CORS.

Пример unit-файла systemd:

```ini
[Unit]
Description=Robot-Buhgalter sync server
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=robotbuh
WorkingDirectory=/opt/robot-buhgalter
ExecStart=/usr/bin/node server/index.mjs
Environment=PORT=8787
Environment=ALLOWED_ORIGINS=https://buh.example.lan
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadOnlyPaths=/opt/robot-buhgalter

[Install]
WantedBy=multi-user.target
```

Проверка, что переменная задана верно: значение `ALLOWED_ORIGINS` должно
совпадать с origin страницы символ в символ — схема, хост и порт, без
завершающего слэша.

### 5.3. Reverse proxy

Пример Caddy. Статика на корне, сервер синхронизации на `/sync`:

```caddy
buh.example.lan {
    encode gzip

    handle_path /sync/* {
        reverse_proxy 127.0.0.1:8787
    }

    handle {
        root * /opt/robot-buhgalter/dist
        try_files {path} /index.html
        file_server
    }
}
```

При такой схеме в п. 5.1 собирать с
`VITE_SYNC_SERVER_URL=https://buh.example.lan/sync`.

Если выберете nginx — важно сохранить два свойства: SPA-fallback на
`index.html` для статики и проксирование `/sync` на `127.0.0.1:8787` без
переписывания тела запроса.

## 6. Требования безопасности

Это не пожелания, а условия задачи.

- **Не публиковать в интернет.** Ни frontend, ни сервер синхронизации. Только
  домашняя сеть или VPN. Причина: у сервера синхронизации **нет авторизации**.
  Он не хранит ключей, но любой, кто до него дотянется, заставит его обращаться
  к API маркетплейсов. Плюс само приложение не имеет входа по паролю — кто
  открыл страницу, тот видит данные.
- **Сервер синхронизации слушает только `127.0.0.1`**, наружу — через reverse
  proxy. Порт `8787` в файрволе не открывать.
- **API-ключи маркетплейсов создавать только на чтение.** Ссылки на разделы
  выдачи ключей есть в самом интерфейсе, на странице «Подключения».
- **Ключи не должны попасть на сервер**: ни в `.env`, ни в systemd-юниты, ни в
  логи, ни в репозиторий. Они вводятся владельцем в браузере.
- **Резервные копии.** Данные живут в `localStorage` браузера — чистка данных
  сайта уничтожит их безвозвратно. Объясните владельцу JSON-экспорт из
  интерфейса и договоритесь о регулярности. Экспорт сознательно не содержит
  API-ключей.
- Если включается шифрование ключей паролем — пароль невосстановим by design.
  Потеря пароля = ключи придётся вводить заново.

## 7. Критерии приёмки

Проверять именно так, с устройства владельца (телефон или ноутбук в домашней
сети), а не с самого сервера:

1. `https://buh.example.lan` открывается, сертификат доверенный, приложение
   отрисовано, в консоли браузера нет ошибок.
2. `https://buh.example.lan/sync/api/health` отдаёт
   `{"ok":true,"service":"robot-buhgalter-sync"}`.
3. На странице «Подключения» индикатор сервера синхронизации — в состоянии
   «доступен», а не «сервер недоступен».
4. В консоли браузера нет ошибок CORS и нет предупреждений про mixed content.
5. Кнопка проверки ключа («Проверить») на одном реальном read-only ключе
   проходит успешно.
6. Синхронизация за период `01.01.2026 – 30.09.2026` по одному кабинету
   возвращает непустой список операций.
7. Включение шифрования ключей паролем работает — то есть WebCrypto доступен,
   secure context настроен верно.
8. `systemctl restart` сервера синхронизации и перезагрузка машины не ломают
   сервис: он поднимается сам.
9. Порт `8787` снаружи недоступен (проверить с другого хоста).

## 8. Чего делать не нужно

- Не разворачивать `server/production/` и PostgreSQL — для этой задачи не нужны
  (п. 1).
- Не трогать существующий production-контур на Hetzner и его базу: это другой
  контур, к домашнему серверу отношения не имеет.
- Не менять привязку публичного домена `kolyman.ru`.
- Не считать `server/index.mjs` «боевым бэкендом» приложения — это только
  прокси к API маркетплейсов.
- Не вписывать ключи маркетплейсов никуда на сервере.
